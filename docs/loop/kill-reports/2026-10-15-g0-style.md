`crates/umber-gui/src/theme.rs`, this report. Plan:

## Built

- `theme::apply(ctx, density, text_scale)`: writes the SAME Umber style to
  both `Theme::Dark` and `Theme::Light` with `set_style_of`. egui keeps a
  style per OS theme and switches on an appearance flip; writing one
  branch lets an OS light-mode flip swap egui's stock light palette over
  the chrome mid-session.
- `umber_style_scaled` now sets three things:
  - `TOOLTIP_DELAY_SECS` = 0.35, the tooltip rest delay. egui's 0 flashes
    tooltips while the pointer crosses the toolbar.
  - `TOOLTIP_WIDTH` = 280 px, so long `tr()` strings wrap.
  - thin floating scroll bars, with `interact_handle_opacity = 1.0` so the
    idle handle stays visible.
- 2 tests:
  - `apply_writes_both_theme_branches`: after `set_theme(Light)` the panel
    fill is still Umber's.
  - `style_sets_tooltip_and_scroll_tokens`.

## Judgment calls

1. **No call site switched yet.** The app still applies `umber_style` per
   chrome `Ui` (toolbar, status bar). Calling `apply` at boot restyles
   every panel at once, and the old plan deliberately held that back
   until the panels migrate. Most have now: postfx, brush, and the slider
   sweep in flight. The boot wiring is the G0 integration commit, after
   the sweep lands, so the restyle and the migration share one visual
   review.
2. **The debug live token reload is deferred.** It needs a token
   override map over `palette::*` constants, which are `const` today. That
   is a theme-model change (consts → a `Tokens` struct), not a G0 fix.
   It is re-queued under G7 polish.
