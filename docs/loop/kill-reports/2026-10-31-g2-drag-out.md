## Scope

Painter's Assets window "drag-out": dragging a library asset out of the
window lands a copy on the filesystem. egui/winit cannot hand OS file
drags OUT of the window, so the implemented surface is: releasing an
asset drag outside every drop target opens a save dialog and byte-copies
the asset's original library file there.

## What landed

- `layers_panel.rs`: pub ctx.data ids (`ASSET_DRAG_SEEN_ID`,
  `ASSET_DRAG_IN_FLIGHT_ID`, `ASSET_DROP_CONSUMED_ID`); `DropTracker::finish`
  sets the consumed flag when it takes an `AssetDrag` payload (a drop,
  not a drag-out).
- `document.rs`: `smart_file_for(dirs, ext, name, load_name)` — resolves an
  asset NAME to its on-disk `.umbersmart`/`.umbermask` file (first dir
  wins, sorted — the listers' dedup rule); `load_name` is the testable
  seam. Pinned unit test `smart_file_for_resolves_by_name_first_dir_wins`.
- `main.rs`: `poll_asset_drag_out`, called at the END of `fn ui` (after
  the dock): detects the AssetDrag payload's in-flight → gone transition;
  if the Layers panel did not consume it, resolves the source file and
  `rfd` save-dialog + `std::fs::copy`; success posts an info notice,
  failure `notify_error`. Cancelled dialog = silent.
- i18n: `assets.drag-out-saved` / `assets.drag-out-failed` in BOTH
  catalogs; `.drag-to-layers` hover now also names the drag-out gesture
  (en + pt).

## Known semantics / deferred tails

- True OS-level file drag-out (drop onto the desktop/file manager) needs
  a winit/OS custom DnD path egui does not expose; the save dialog is the
  v1 surface, documented as such.
- Brush presets stay click-only (a brush is not a layer, and not a
  file asset in the library dirs) — unchanged.
- The detector is frame-transition based (in-flight → gone), so it works
  regardless of which panel runs first in the dock.
